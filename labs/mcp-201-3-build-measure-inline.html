Phase 2

Pattern

Pre-write validation

The policy action consumes the department returned by employee lookup. Its rejection response is followed by an explicit stop, so the write path cannot run.

2.1

Make policy consume the employee result

The fragmented client could invent or reuse a department. The Process branch has an employee result available, so the policy action can consume the authoritative value directly.

Overview

Making one step consume another step's output turns a suggested sequence into an enforced data dependency. ▲ EMP-0005 belongs to DEPT-0002; do not derive one identifier from the other. Map the department datapill returned by the supplied lookup.

  • Inspect the supplied Get employee action and locate its department_id output.
  • In the visually marked learner-editable region, add the connector's Check policy limits action.
  • Map department_id from Get employee → department_id.

  • Save and inspect the action inputs once more before continuing.
Verify the policy action is inside the marked region, before the write, and its department input visibly traces to the supplied employee lookup.
2.2

Reject and stop before the write

A policy verdict is not enough. The caller needs a stable outcome, the violated rule, the observed and allowed values, a correction, and certainty that the rejected request did not continue into a write.

Overview

You end with a non-compliant conditional that returns rejected_policy and immediately stops without error. The response uses values returned by the policy action rather than hardcoded limits.

Heads up

Return does not stop execution

A Return response sends data to the caller, then the recipe can continue. Without a following Stop, a green job can return a rejection and still create the expense report.

Policy rejection
FieldValue
ConditionCheck policy limits → compliant is false
outcomerejected_policy
messageInclude violated rule, observed amount, allowed amount, corrective action, and that no report was created
report_idLeave empty
Stop with errorNo
Detailed steps 7 steps

The response makes the rejection actionable; the explicit stop makes its no-report claim true.

  • Add an IF after Check policy limits for a non-compliant result.
  • Inside that branch, add Return response and set outcome to rejected_policy.
  • Build message from the policy result so it names the violated rule, observed amount, allowed amount, corrective action, and no-report state.
  • Leave report_id empty.
  • Add Stop immediately after the response and set Stop with error to No.
  • Trace the rejection branch top to bottom and confirm it cannot reach the supplied create action.
  • Record on handout question 1 whether your edits remain limited to the description and marked policy region.
Verify the non-compliant path is Check policy limits → IF → Return response → Stop, returns the exact rejected_policy value with all four actionable details, and ends before any write.

4.2

Compare the designs without pooling the paths

Fewer calls matter only after the process did the right thing. The three paths differ, so each one needs its own conclusion.

Overview

If you get stuck

  • The separate skeleton is missing. Do not begin the walk-through [ENV-DEP: Lab 3 Process skeleton project and server].
  • You edited supplied logic outside the two permitted locations. Restore from the complete shared reference project, then restart from the skeleton [ENV-DEP: shared Lab 3 reference-solution project].
  • A rejection still creates a report. Stop testing and inspect the explicit Stop after your Return response.
  • A connector action or field differs from the guide. Mark the exact step and UI label for routing; do not guess [ENV-DEP: validated Workato UI path].
  • Both servers are attached. Detach one and rerun that prompt in a fresh conversation.
  • The environment needs cleanup. Use only the event procedure; do not improvise deletion [ENV-DEP: documented reset procedure].

Reflect

Now that one branch has been tested against a valid request and two policy violations, consider what the evidence can and cannot establish.

  • Which evidence showed that a rejection stopped the write rather than only describing one?
  • Why does prompt 1 have to pass before the two rejection results mean anything?
  • What control is still missing when someone asks to file for the CEO, and why did composition not add it?
  • Which part of the design belongs in the tool description, and which belongs in deterministic recipe logic?

Wrap-up

Noor's valid expense filed, while both policy-sensitive requests were stopped before report creation—provided every required ledger check passed.

  • Atomic intent. Submission owns its required sequence; status remains separate.
  • Pre-write policy. The employee lookup supplies the department and the rejection path stops before the write.
  • Semantic outcome. rejected_policy says what rule failed, what values were compared, and what to do next.
  • Correctness before efficiency. Each paired row reports the business result before calls and time, with no pooled claim.

Keep the project unchanged for the debrief. During internal testing, record setup and lab duration separately; the 70-minute value remains an estimate until a first-time run is timestamped.
