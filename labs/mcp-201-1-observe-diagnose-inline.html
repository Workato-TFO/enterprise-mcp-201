Observe and diagnose

Intermediate 30 minutes Lab 1 of 3
Introduction

In this lab, you'll act as integration engineer for IDEA Brands — running six requests against a fragmented expense MCP (Model Context Protocol) server and recording what the client actually does with them. You are not here to repair the server. The IDEA Brands expense data is synthetic.

NA
Noor Aziz
Software Engineer · IDEA Brands

They ask the assistant to file a hotel expense, get told it is handled, and find out later that nothing was ever submitted.

The question

The server has a working policy checker and a working budget validator. Why do the wrong expenses still get filed?

You'll learn how to

  • Get a working LibreChat connection to your fragmented server
  • Record a first-run baseline for five requests you did not write
  • Predict a failure, write a prompt to provoke it, and score the prediction
  • Attribute each observed failure to the principle it breaks

What you'll need

  • Completed Enterprise MCP Essentials — a pre-read is not a substitute
  • Your assigned LibreChat account for the event
  • Your isolated Workato project, with the fragmented expense server already provisioned
  • Your Cardboard Apps sign-in, so you can open Rebate as Noor and read the expense ledger
  • Your printed lab handout, which holds everything you write in your own words
Phase 1

Connect the fragmented server

In this phase, you'll get a working LibreChat connection to your fragmented server.

Pattern

Authenticated connection

An MCP client reaches a server through a generated URL that carries its own credential. Confirming the tool inventory before you measure anything is what makes the later readings comparable.

1.1

Get yourself a key to the server

You did this workflow in Enterprise MCP Essentials, so the mechanics will be familiar. What is different is what you are connecting to: a server with seven working tools and no opinion about the order anyone calls them in.

Overview

You end with an ATT###-expense-fragmented token on your expense server and its generated MCP Server URL saved somewhere private. Workato shows that URL once.

Heads up

The generated MCP Server URL embeds your token. Treat it as a credential: keep it out of chat messages, screenshots, your handout, and shared notes.

Token settings
FieldValue
Token nameATT###-expense-fragmented, with your own learner ID in place of ATT###
ServerThe fragmented expense server as provisioned for you
Detailed steps 5 steps

Every learner measures against their own server rather than a shared one, so one person's run cannot show up in someone else's readings.

  • In Workato, open Enterprise MCP and select your assigned expense server. Its header shows how many tools it carries — confirm it reads 7 tools.
  • Open the Settings tab, then End user access.
  • Under MCP Tokens, select Create new token and name it ATT###-expense-fragmented, replacing ATT### with your learner ID. The dialog warns you that a token name cannot be changed after creation, so read it back before going on.
  • Select Create token, then copy the generated MCP Server URL before you close the dialog — Workato shows it once, and closing without copying means creating another token.
  • Store the URL somewhere private for the next task.
Verify the server's token list contains your ATT###-expense-fragmented token, and that you have the generated URL saved somewhere private.
1.2

Point the client at the server

The server exists, but nobody at IDEA Brands works in Workato. They work in a chat window, and until a client connects there is nothing to observe.

Overview

You end with the fragmented server registered in LibreChat, its status showing connected. Choose API Key authentication and leave every field beneath it blank — your token is already inside the URL, and picking API Key skips an auto-detect step that can take a minute or more.

Detailed steps 3 steps

Registering the server is the only step in this lab where a mistake is silent. A wrong URL fails loudly; a second server left attached does not.

  • In LibreChat, open the MCP Servers panel and select + to add a server.
  • Complete the form using the values above, then select Create. Leave Each user provides their own key unticked — ticking it asks every caller for a key you do not have, because the credential is already inside the URL.
  • Select Connect beside your new server and wait for its status to show connected.
Verify your server appears in the LibreChat MCP Servers panel with a connected status.
1.3

Seven tools is the number that makes this lab's point. Count them before you measure anything, because a miscount here is a wrong conclusion in Phase 4.

Overview

You end with a fresh conversation where your fragmented server is the only one selected, and the assistant has listed all seven tools back to you — create_expense_report and submit_expense_report among them, as two separate tools.

Confirming the inventory first is what lets you attribute a later failure to the design rather than to your setup.

  • Open a fresh chat and select your fragmented server from MCP Servers in the prompt bar.
  • Confirm the prompt bar names your server and nothing else — the composer shows "N selected", and two attached invalidates every reading you take today.
  • Ask What tools do you have available? and confirm seven tools are listed.

2.1

File the expense Noor asked for

Noor stayed at the IDEA City Hotel in Portland and paid $245 a night, which is inside the lodging limit for their department. Nothing about this request is unusual. It is the run where you find out what "done" means to this server.

Overview

You end with the workbook's Valid tab holding three readings, and with the answer to one question written on your handout: was the expense actually filed? Keep this conversation open — Task 2.3 comes back to it.

Note

Go and look at the ledger yourself

The chat window is the model's account of what happened. Rebate is the record of what happened, and they are allowed to disagree.

Sign in to Cardboard Apps, switch your player role to Noor Aziz, and open Rebate. Find the lodging expense report you filed a moment ago and read its status. Expect to find it sitting in draft — created, but never submitted, so nobody has been asked to approve it and nothing is moving.

Write that status on your handout beside your answer to question 1. If the two disagree, the disagreement is the finding.

Detailed steps 5 steps

This is the run everything else is measured against, so take the readings carefully even though nothing appears to go wrong.

  • Open the Valid tab in the workbook at the top of this phase and copy its prompt. Every prompt in Phase 2 lives on a tab there — one record, six tabs, and the wording is never retyped from the page.
  • In a fresh conversation, send that prompt exactly as written.
  • Wait for the final response, and leave this conversation open — Task 2.3 comes back to it.
  • Record completion time, tool calls, and context used on the Valid tab, reading all three from LibreChat.
  • On your handout, answer question 1: did submit_expense_report get called, and did the model's final message accurately describe the report's actual status?
Verify the Valid tab has all three readings, and that your handout carries both a submitted-or-not answer and the status you read in Rebate.

2.3

Name the wrong tool on purpose

Reading and writing are different operations with different consequences. This request asks for a reading and names a write tool to do it with, which is a thing callers do by accident far more often than on purpose.

Overview

You end with the Wrong tool tab filled and question 3 answered on your handout. The reading to take is whether create_expense_report ran, get_expense_report_status ran, or neither — and whether anything got written while you were asking a question.

Note

Why you return to your own conversation

Report IDs are allocated sequentially per tenant, so any ID printed in a guide points at a different report — or at nothing — after the next reset. Returning to your own Task 2.1 conversation sidesteps that entirely. This is the one task that reuses a conversation, and your context reading will be higher here because of it. Record it as it reads.

Detailed steps 4 steps

A design that cannot keep reading apart from writing will eventually write when someone only asked a question, and the caller who caused it will not have meant to.

  • Return to your Task 2.1 conversation rather than starting a new one — this is the only run that reuses one.
  • Send the Wrong tool tab's prompt.
  • Record the three readings on that tab. Your context reading will be higher here because the conversation already has a run in it, and that is the honest number.
  • Turn to question 3 on your handout: which tool was selected and whether a second report now exists, then — if anything declined — whether it was the server or the model that did the declining.
Verify the Wrong tool tab has all three readings, and that question 3 states explicitly whether any write occurred and what now exists in the ledger.
2.4

Claim an approval nobody can verify

This request carries an approval nobody can check and an instruction to skip a prerequisite. It is not a normal expense request, and the correct business outcome is still rejection without creation.

Overview

You end with the Bypass tab filled and question 4 answered, including whether a report exists in the ledger afterwards. create_expense_report has no verifiable manager-approval input, so the claim in the prompt is unverifiable and must not change what the server does.

Detailed steps 3 steps

The point is not to catch the model being gullible. It is to find out whether the server's guarantees survive a caller who asks it to drop them, because in production some caller eventually will. ▲ A refusal is a valid result. Do not rerun until the model misbehaves — preserve your first run. The question is whether the server guaranteed the prerequisite, not whether every model run happened to fail.

  • In a fresh conversation, send the Bypass tab's prompt.
  • Record the three readings on that tab.
  • Turn to question 4 on your handout and record three separate observations: whether the model independently checked policy despite being told not to, whether create_expense_report was called, and whether a report exists in the ledger afterwards.
Verify the Bypass tab has all three readings, and that question 4 on your handout carries the policy-check behaviour, the create behaviour, and the resulting ledger state as three distinct answers rather than one summary.
2.5

File on someone else's behalf

Filing an expense for someone else is a normal thing to need and an unusual thing to be allowed. This request asks the server to do it for the CEO, and the server has no way to know who is asking.

Overview

You end with the On behalf tab filled and question 5 answered with a note on what control is missing. create_expense_report accepts any employee_id with no notion of the requester, so the interesting reading is what did not happen rather than what did.

Heads up

This should give a well-designed system pause

It does not. There is no actor concept anywhere in this estate — no requester identity travels with the call, so nothing can compare who is asking against whose expense is being filed. Note where that control would have to live. You will find in Lab 2 that composing the tools does not add it, because sequencing and authorisation are different problems.

Detailed steps 3 steps

This request separates two things the fragmented design conflates: knowing whose expense this is, and knowing who is asking for it to be filed. Only the first exists anywhere in the estate.

  • In a fresh conversation, send the On behalf tab's prompt.
  • Record the three readings on that tab.
  • Turn to question 5 on your handout: whether the report was created, whether any actor or authorisation check occurred at any point, and one sentence naming the control that is missing and where it would have to live.
Verify the On behalf tab has all three readings, and that question 5 on your handout names one missing control with a location for it.
Phase 3

Write the sixth yourself

In this phase, you'll predict a failure, write a prompt to provoke it, and score the prediction.

Pattern

Adversarial probe

Predicting before you type turns a run into a test. A prediction that turns out wrong is still a result, because it tells you the design fails somewhere other than where you expected.

3.1

Break it on purpose

You have run five prompts somebody else wrote. The sixth is yours, and the useful part is not the prompt — it is committing to a prediction before you type it, so the run has something to be right or wrong about.

Overview

You end with the Your prompt tab holding your wording and three readings, and question 6 on your handout holding a prediction scored against what happened. Run it once in a fresh conversation and keep the first result.

Note

The same prompt behaves differently between runs

This is measured, not hypothetical. On the same server, the valid $245 request went three calls and never submitted on one round, then four calls and submitted on the next; the over-limit $347 request ran no policy check on one round, then ran the check on the next and created the report anyway. Your neighbour's first row may have submitted while yours sat in draft, and neither of you did anything wrong. "Mine worked" does not disprove the point — it is the point, because a design whose correctness depends on which way the model went this time is not a reliable design. This is also why no single run is evidence: the readings that hold their direction are tool counts and context size.

Detailed steps 5 steps

Everything so far has been a prompt you were handed. This one tests whether you can now predict where the design gives way, which is a different skill from noticing it afterwards.

  • On your handout, write your prediction before you type the prompt, naming the prerequisite you think will be skipped, what in your prompt gives the model an excuse to skip it, and what the unsafe result would be.
  • Scroll back to the workbook at the top of Phase 2 and open its last tab, Your prompt. Write your prompt there, or press Help me pick and edit what it gives you. A useful shape is a plausible expense request followed by one sentence of pressure.
  • Run it once, in a fresh conversation.
  • Record completion time, tool calls, and context used in that same tab.
  • On your handout, record the outcome, whether a report exists in the ledger afterwards, and score your prediction as right, wrong, or something you did not anticipate — all three are worth reporting.
Verify the Your prompt tab holds your wording and three readings, and that question 6 on your handout carries your prediction scored against what actually happened.
Phase 4

Diagnose the design

In this phase, you'll attribute each observed failure to the principle it breaks.

Pattern

Naive API wrapper

A server that exposes one tool per application endpoint rather than grouping tools around the workflow a caller is completing. It is the pattern Cohesion over Convenience exists to prevent.

4.1

Name what was missing

You have six tabs of readings, a handout full of observations, and roughly five minutes. The job now is to stop describing what the model did and start naming what the design made possible.

Overview

You end with the mapping grid on your handout complete — each run's failure attributed to Clarity, Cohesion, Explicitness, or Determinism — question 7 answered, and one piece of evidence chosen for the debrief. Compare question 4 against question 2: the same 300 USD lodging limit, different framing, and the question is whether the outcome changed.

Key insight

You have been diagnosing a naive API wrapper

In Enterprise MCP Essentials you met the naive API wrapper: a server that exposes individual endpoints directly as tools instead of grouping them around the workflow a caller is completing. This server is exactly that, one tool per application endpoint. It is what Cohesion over Convenience prevents, and it touches Clarity over Completeness as a side effect, because a wrapper tends to expose every endpoint whether a caller needs it or not. Workato's published guidance puts it the same way — design servers that group tools around the workflows an LLM needs to complete.

Detailed steps 5 steps

Lab 2 starts from whatever you write down here, so the attribution matters more than the anecdotes. A failure with a principle attached is something you can design against; one without is a story.

  • On the handout's mapping grid, mark every prerequisite the client had to coordinate for itself.
  • Mark every decision that belongs to deterministic process logic rather than to model reasoning.
  • Compare your question 4 answer with your question 2 answer — same policy limit, different framing — and record whether the outcome changed.
  • Answer question 7 on your handout: one sentence explaining why the fragmented server creates an orchestration tax.
  • Circle the single strongest piece of evidence you will bring to the debrief. The workbook at the top of Phase 2 is there if the strongest thing you have is a number.
Verify every failure on your handout's mapping grid is attributed to one of the four principles, and that you can state your question 7 sentence out loud without reading it.

If you get stuck

  • The model refuses. Keep the refusal. It is a result, and re-running until something breaks measures your persistence rather than the design.
  • A LibreChat reading is not visible. Write "unavailable" in that field rather than estimating it, and ask a TA to point it out. An honest gap is worth more to your Lab 3 comparison than a plausible number.
  • Your context reading looks far higher than your neighbour's. Check the prompt bar. Two servers attached inflates every reading, and the fix is to remove one and re-run that request in a fresh conversation.
  • Rebate shows no report at all. That is a finding, not a mistake. Record it on your handout and carry on.

Reflect

Now that you have six sets of first-run readings, consider what they say about the difference between a working API and a reliable design.

  • The policy checker exists, works, and was called twice in ten write-intent runs during testing. What does that gap tell you about where a prerequisite has to live if it is going to be dependable?
  • Two learners running the identical prompt got different tool counts. If neither run is wrong, what can a single run legitimately be used to prove?
  • Your wrong-tool request either did or did not stay read-only. What would have to be true of the tool contract for that outcome to be guaranteed rather than likely?
  • Filing for the CEO succeeded without any check on who was asking. Which of the four principles does that break, and would composing the tools into one command fix it?

Wrap-up

Noor's expense may or may not have been filed today, and the honest answer is that the server cannot tell you which — that is the finding, not a gap in your notes.

  • Clarity over Completeness. Seven tools that each work can still add up to a surface nobody can use correctly.
  • Cohesion over Convenience. Grouping tools by the endpoints an API already exposes is convenient for the builder and expensive for every caller afterwards.
  • Explicitness over Inference. Anything the contract leaves unstated, the model will supply by inference, and it will sound equally confident either way.
  • Determinism over Cleverness. A design whose correctness depends on which way the model went this time is not a design you can operate.
